01 — Context

Context

Hazus is a hazard analysis platform used by federal agencies, urban planners, emergency managers, and hazard mitigation professionals to assess risk from natural disasters.

Despite its importance, the existing workflow for conducting location-based risk analysis is built on an outdated desktop system that has not kept pace with modern user experience standards.

Current Design

02 — Problem

Problem

Defining the geographic boundary is the first step when creating a hazard analysis in Hazus. Analysts must specify the exact region they want to study, which can range from an entire county to a small census block.

In the existing system, selecting these boundaries relied heavily on ArcGIS-based hierarchical navigation. Users were required to drill down through multiple geographic levels in a rigid sequence, often mirroring the underlying GIS data structure rather than the analyst's actual workflow.

Core problems identified

01
Unconventional design standards

The interface was built around complex GIS design patterns rather than modern web application standards. This created a steep learning curve for new users and made simple tasks unnecessarily difficult.

02
Rigid hierarchical navigation

Selecting a geographic boundary required drilling down through multiple administrative layers. Analysts who already knew their target location still had to navigate through unnecessary intermediate steps.

03
Long loading time due to large amount of data

Each jurisdictional layer contains a vast amount of flood data. When users attempt to switch from one layer to another, it takes a long time for the changes to appear on the map. Users often became confused or mistakenly believed that an error had occurred.

03 — Research Approach

Research Approach

Traditional user interviews were not conducted for this project. Instead, the team worked through a structured process of client workshop sessions and business requirement reviews, translating domain expertise and organizational priorities directly into design decisions.

Three primary user groups were identified across the feedback process:

Primary
Government Staff

Need to access location data without extensive GIS knowledge.

Secondary
Technical Specialists

Hazard analysts and urban planners who need speed and directness.

Secondary
Emergency Managers

Require clarity and confidence in their location selections under pressure.

User needs

View hazard information within a web-based application to understand the geographic details of the analysis.

Select a geographic area directly on the map to initiate hazard analysis.

Understand potential impacts within a jurisdiction to plan mitigation and response strategies.

Product Goals

  • Keep location selection on the map itself — Avoid dropdowns or form-based inputs that pull focus away from the map.

  • Make every map element communicate clearly — Users should always know what is selected, what is active, and what isn't without having to guess

  • Always make path simple and clear — Move away from the rigid drill-down hierarchy and design a more natural way to interact with geographic boundaries

04 — Ideation

Ideation

To simplify this process, I explored a way that would allow analysts to first select a state and then directly choose the geographic boundary type they needed (county, community, or census block) without requiring a strict hierarchical drill-down.

  1. Concept 01 — Dropdown-based Jurisdiction Selection

    • Users select location through a state → county → city dropdown sequence in the sidebar
    • Didn't work when analysts needed jurisdictions from different parent regions which required a full rework each time
    • Difficult to use alongside a full-screen map, leaving limited space for both panels to display

  1. Concept 02 — Automatic Boundary Calibration

    • Boundary type changes automatically based on zoom level. State at wide view, down to tract and block as the user zooms in
    • Intuitive for exploration, but offered no explicit way to select or confirm a jurisdiction for analysis
    • Stakeholders raised concerns about loading performance, and it was unclear whether this approach would make things better or worse

  1. Concept 03 — Hybrid Map and Search

    • A search bar initiates selection by focusing the map on a single state, then revealing boundary options
    • Locking users into one state at a time didn't match how regional analysts scope multi-state work
    • Multi-state selection remained an open problem, but incorporating search showed clear potential worth carrying forward
04 — Design Decision

Key Design Decisions

To simplify this process, I explored a way that would allow analysts to first select a state and then directly choose the geographic boundary type they needed (county, community, or census block) without requiring a strict hierarchical drill-down.

Guided navigation for boundary selection

Introduce a structured navigation panel that lets users select a state first, then choose the geographic boundary type they need, without following a rigid hierarchy.

Clear visual feedback on the map

Design eye-catching map symbology to clearly highlight selected jurisdictions, helping users immediately understand which geographic area is currently active.

Summary panel for selected jurisdiction

Provide a summary panel that displays the selected location and boundary level, letting users quickly verify their selections.

Improve location selection with a better search experience.

Enhance the search functionality so users can quickly find a specific jurisdiction without manually navigating through multiple geographic layers.

05 — Final Design

Final Design

The redesigned Interactive Map Viewer consolidates the geography selection step onto a single, unified canvas, allowing analysts to pick a state, switch between boundary types, and preview their selection without leaving the map.

Step 01

Opening Page

The analyst lands on the full U.S. map. Two entry points are available: selecting a state directly from the map, or searching by state, county, or city through the search bar in the top right.

Step 02

State

Once a state is selected — here, Virginia — the analyst can drill down to County, Community, Census Tract, or Census Block. Map boundaries redraw to match the chosen jurisdiction type.

Unlike the legacy flow, analysts aren't forced to step through every jurisdiction level sequentially. They can jump directly to the level they need.

Step 03

Lower Level Jurisdiction

With Virginia selected and County chosen as the jurisdiction type, the map recalibrates to display every county boundary within the state. Switching to Community or Census Tract redraws the borders to match the new selection.

Step 04

Selecting County

Selecting an individual county shifts the parent state boundary to a neutral tone, keeping visual focus on the jurisdiction level the analyst is actively working on. A summary modal opens next to the selection with location details and an option to "Add to List"

Look up by Search

If an analyst already knows the location by name, FIPS code, or jurisdiction ID, the search bar in the top right is a faster way to find it than navigating the map.

Summary Panel

As analysts select locations on the map, a summary panel on the right tracks what has been added to the study area.

Selections are organized as a tree — State → County → Community — so the analyst can see both the hierarchy and the specific boundaries in play at a glance.

Colored Symbology

The old Hazus symbology used dense pattern and outlines experts could read but general users could not. For the updated version, I rebuilt the palette using the U.S. Web Design System, pairing fill colors with clear border weights and styles to show different jurisdiction levels and states (Active, Added to List).

06 — Outcomes & Reflection

Outcomes & Reflection

The redesign transformed OpenHazus from a tool that required specialist knowledge into an interface accessible to all user groups regardless of GIS background.

What was achieved

This project was descoped following a federal funding cut. With limited time to wrap up, the team prioritized delivering the core MVP and made a number of adjustments to the original product goals. The outcomes below reflect what was completed within those constraints.

01
Modern design standards adopted

The tool now aligns with modern web conventions, significantly reducing the onboarding barrier for new users.

02
Direct jurisdiction access

The legacy pyramid flow is replaced, users can now reach their target location in a single step, eliminating unnecessary navigation for both expert and non-specialist users.

What I learned

Working within constraints, whether due to limited research or technical challenges, does not require compromising design quality. It requires being more deliberate about the reasoning behind each decision.

Collaborating with other UX designers strengthened my ability to quickly align on direction and present a unified perspective to stakeholders, even when internal views differed.

What I Would do differently

I would validate the jurisdiction model earlier in the process. Jumping into the design without fully understanding the jurisdiction model made the process much harder. We went through many rounds of trial and error, which caused a lot of delays.

I could've pushed my designs a bit further. The whole of this project was to branch out from the desktop application, which was the more technical version, and build something that is more user intuitive and focus more on the user's experience over the technical aspects. However, as we were working, team raised concerns about being too different from the original desktop application.
