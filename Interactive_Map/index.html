Case Study · 01 — OpenHazus

Interactive Map Viewer

Redesigning the geography selection step of a hazard analysis workflow — making geospatial boundary selection accessible to analysts across all technical backgrounds.

01 — Context

Context

Hazus is a hazard analysis platform used by federal agencies, urban planners, emergency managers, and hazard mitigation professionals to assess risk from natural disasters.

Despite its importance, the existing workflow for conducting location-based risk analysis is built on an outdated desktop system that has not kept pace with modern user experience standards.

02 — Problem

Problem

Defining the geographic boundary is the first step when creating a hazard analysis in Hazus. Analysts must specify the exact region they want to study, which can range from an entire county to a small census block.

Defining the boundary is the first step in creating a hazard analysis in Hazus. To do this, analysts must specify the region they want to study. This region can be as big as a county or as small, as a census block. The old system made it hard to select these boundaries. It used ArcGIS to navigate through levels in a strict order. This order was based on the GIS data structure not how analysts really work. Analysts had to navigate through levels to select their region. This was not flexible. Did not match their workflow.

Core problems identified

01

Built for GIS experts, not analysts

The interface was built around complex GIS design patterns rather than modern web application standards, creating a steep learning curve for non-specialist users.

02

Rigid hierarchical navigation

Selecting a geographic boundary required drilling down through multiple administrative layers. Analysts who already knew their target location still had to navigate through unnecessary intermediate steps.

04 — Understanding the Problem

Understanding the Problem

Research was conducted through structured client workshops with subject matter experts who work alongside analysts daily, and through systematic review of existing business requirements documents.

Three primary user groups were identified across the feedback process:

Primary
Government Staff

Knows exactly which census block they need to study but can't get there without navigating through layers they don't need.

Secondary
Technical Specialists

Experienced enough to work around the interface but frustrated by how many steps it takes to do something they've done dozens of times.

Secondary
Emergency Managers

Working with too many data at once. The last thing they need is uncertainty about whether they selected the right jurisdiction.

User needs

Select a study area quickly and with confidence, without needing to understand the GIS data structure.

See exactly what's selected on the map at all times.

Find a specific jurisdiction by name without navigating through layers to get there.

Product Goals

  • Keep location selection on the map itself — Avoid dropdowns or form-based inputs that pull focus away from the map.

  • Make every map element communicate clearly — Users should always know what is selected, what is active, and what isn't without having to guess

  • Always make path simple and clear — Move away from the rigid drill-down hierarchy and design a more natural way to interact with geographic boundaries

05 — Ideation

Ideation

To simplify this process, I explored a way that would allow analysts to first select a state and then directly choose the geographic boundary type they needed (county, community, or census block) without requiring a strict hierarchical drill-down.

  • Concept 01 — Dropdown-based Jurisdiction Selection

    • Users select location through a state → county → city dropdown sequence in the sidebar
    • Didn't work when analysts needed jurisdictions from different parent regions which required a full rework each time
    • Difficult to use alongside a full-screen map, leaving limited space for both panels to display

    A side panel showing the active jurisdiction and its relationship to the parent level was definitely a keeper

  • Concept 02 — Automatic Boundary Calibration

    • Boundary type changes automatically based on zoom level. State at wide view, down to tract and block as the user zooms in
    • Intuitive for exploration, but offered no explicit way to select or confirm a jurisdiction for analysis
    • Stakeholders raised concerns about loading performance, and it was unclear whether this approach would make things better or worse

  • Concept 03 — Hybrid Map and Search

    • A search bar initiates selection by focusing the map on a single state, then revealing boundary options
    • Locking users into one state at a time didn't match how regional analysts scope multi-state work
    • Multi-state selection remained an open problem, but incorporating search showed clear potential worth carrying forward

    Search integration showed clear potential for faster location lookup and carried into the final design as a map-integrated search bar.

Each concept consisted of something worth carrying forward. The boundary selector buttons and a jurisdiction summary panel from Concept 01, and the case for map-integrated search from Concepts 02 and 03. The final design draws on all three while addressing the visual feedback problem that none of them fully solved.

06 — Design Overview

Design Overview

Guided navigation for boundary selection

Introduce a structured navigation panel that lets users select a state first, then choose the geographic boundary type they need, without following a rigid hierarchy.

Analysts already knew their target location. The interface shouldn't force them to prove it by stepping through every level.

Clear visual feedback on the map

Design eye-catching map symbology to clearly highlight selected jurisdictions, helping users immediately understand which geographic area is currently active.

Without clear visual cues, users constantly second-guessed whether their selection had registered.

Summary panel for selected jurisdiction

Provide a summary panel that displays the selected location and boundary level, letting users quickly verify their selections.

Analysts needed to see not just what was selected, but how it fit into the broader hierarchy — State → County → Community.

Improve location selection with a better search experience

Enhance the search functionality so users can quickly find a specific jurisdiction without manually navigating through multiple geographic layers.

For analysts who already knew the jurisdiction name or FIPS code, navigating the map was an unnecessary detour.

06 — Final Design

Final Design

The redesigned Interactive Map Viewer consolidates the geography selection step onto a single, unified canvas, allowing analysts to pick a state, switch between boundary types, and preview their selection without leaving the map.

Step 01

Opening Page

The analyst lands on the full U.S. map. Two entry points are available: selecting a state directly from the map, or searching by state, county, or city through the search bar in the top right.

Step 02

State

Once a state is selected, such as Virginia, the analyst can choose any boundary type directly: County, Community, Census Tract, or Census Block. No forced sequence and map boundaries will redraw to match the selected jurisdiction.

Step 03

Lower Level Jurisdiction

With Virginia selected, choosing County redraws the map to show all county boundaries within the state. Switching to Community or Census Tract updates the view instantly with no page reload, no waiting.

Step 04

Selecting County

Selecting a county dims the parent state boundary, keeping focus on the active jurisdiction. A summary modal appears next to the selection, showing location details and a one-click option to add it to the study area.

Look up by Search

If an analyst already knows the location by name, FIPS code, or jurisdiction ID, the search bar in the top right is a faster way to find it than navigating the map.

Summary Panel

As analysts select locations on the map, a summary panel on the right tracks what has been added to the study area.

Selections are organized as a tree — State → County → Community — so the analyst can see both the hierarchy and the specific boundaries in play at a glance.

Colored Symbology

The legacy symbology relied on dense patterns and outlines that only users with GIS training could interpret. The updated palette was rebuilt using the U.S. Web Design System, pairing distinct fill colors with border weights and dash patterns to communicate jurisdiction level and selection state at a glance.

Outcomes & Reflection

This project was delivered under significant constraints like shifting requirements, evolving scope, and project descoping due to federal budget cuts. The team prioritized delivering a functional MVP and made deliberate trade-offs to get there.

Further exploration
Brainstormed Ideas
Explored
  • Multi-state county selection — allowing analysts to select jurisdictions across state boundaries without restarting the flow
  • Iterated search experience — a refined version of the search feature addressing edge cases from the initial presentation
  • Symbology — a full visual language for jurisdiction levels and selection states built on USWDS
  • Post-selection confirmation flow — a step to review and confirm the full study area before proceeding to analysis

What I learned

Validate the domain model first

The jurisdiction hierarchy proved to be more complex than initially anticipated. Early misalignment with this model led to project delays, as designs had to be revised each time additional complexity emerged.

Build shared understanding across the whole team

In projects involving a highly specialized knowledge, it is important to take the time to align all participants including stakeholders, and leads. Without the foundational alignment, I was often left to address the gaps on my own.

Define "done" before you start

Scope changes frequently occur in government contracts. However, establishing explicit agreement on the definition of completion for each phase provides the team with a consistent reference point when priorities shift.

What I would do differently

01

Map and validate the jurisdiction model before opening Figma. A simple diagram would have prevented weeks of iteration.

02

Push for explicit MVP definitions at the start, with clear agreement on what "done" looks like at each phase, so when scope shifts, the team has a fixed reference point to return to.
